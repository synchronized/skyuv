# 010：Windows 构建诊断治理

## 状态

已完成。诊断治理、缺陷补丁、Windows 本地矩阵、Linux/macOS CI 与三平台发行演练均已通过。
公开预览发布状态以 [beta.4 版本文档](../versions/v0.2.0-beta.4.md)为准。
计划作为 `v0.2.0-beta.4` 的独立预览范围，承接未发布 beta.2 规划，不等待固定 Linux 性能 Runner。

## 背景与目标

Windows 构建输出包含大量第三方警告及随附说明，影响新增问题的识别。
先建立可重复的诊断基线，再修复可证明的问题，记录必须保留的诊断。
首轮采样见 [构建诊断记录](../records/windows-build-diagnostics.md)。

## 不在范围内

- 不全局关闭警告、降低等级或关闭 skyuv 的警告即错误。
- 不直接修改第三方源码，不混入第三方升级或 Actor、网络架构重构。
- 不承诺第三方源码全部零警告，不删除诊断上下文以制造零警告结果。
- 不在本计划中发布正式 `v0.2.0`，也不提前修改当前版本号。

## 设计决策与影响范围

- 自有源码问题在 `src/`、`include/skyuv/` 或测试中修复，保持严格警告策略。
- 编码类问题优先在仓库维护的 CMake 接入层对具体目标设置源编码。
- Windows Microsoft CRT 工具链统一对第三方源码定义 `_CRT_SECURE_NO_WARNINGS`：
  纯第三方目标使用 PRIVATE 定义，混合目标仅设置第三方源文件属性，不传播到自有代码或消费者。
  此规则覆盖 MSVC、clang-cl 和 Clang GNU 前端，不关闭其他弃用诊断及高风险警告。
- 第三方类型转换须证明范围、符号与边界条件；不能靠未经验证的强制转换消除警告。
- 用户确认日常 Windows MSVC/clang-cl 构建仅对 libuv PRIVATE 屏蔽
  C4244/C4245/C4267/C4701/C4152/C4702；统一 `SKYUV_LIBUV_DIAGNOSTICS=ON`
  恢复这些诊断，供依赖升级与定期审查。其他新警告保留；cmocka 使用局部 `/utf-8`。
  不把 155 条转换提示全部修复作为发布前提，保留基线；具体修复仍须边界证据。
- 第三方未初始化、移位和函数指针诊断先核对控制流及平台契约；确有缺陷且无法适配时，
  通过独立、可重复应用的补丁修复并增加复现测试。
- 平台有意使用的扩展或编译器误报，保留证据；如需例外，必须限定目标或最小代码范围，
  记录诊断编号、原因和复查条件，不将 skyuv 警告策略应用于第三方目标。
- `note`、声明位置和“编译源文件”是诊断上下文，不单独计作缺陷；关联主诊断解决后复核。

## 实施步骤

1. 全量重建 MSVC、clang-cl、Clang 的 Debug/Release，记录编译器版本、退出码、
   原始日志及按文件位置和诊断编号去重的清单；避免增量构建漏报及 MSBuild 汇总重复计数。
2. 优先处理 cmocka 编码警告，复核公共头文件被不同目标编译时的编码一致性。
   并优先处理 Windows Clang 的 CRT 弃用和未使用静态函数：审查调用边界后采用目标级
   CRT 宏，unused 标记优先补丁维护；必要例外限于 Windows Clang 的 libuv 目标。
3. 优先审查 libuv 的 C4701 未初始化及 C4334 移位诊断，再审查 C4244/C4267/C4245
   截断和符号转换；每项明确修复、保留或局部例外结论。
4. 复核 C4152 函数/数据指针转换和 C4702 不可达代码，补充平台契约依据。
5. 建立修复前后对比记录，完成三平台验证；更新版本、计划和实施记录后再准备预览发布。

## 测试与验收标准

- 每个诊断类别都有来源、风险、处置方式和验证证据；编码警告消除。
- 自有目标维持严格警告与警告即错误，第三方工作树干净。
- Windows 三种编译器 Debug/Release 完成配置、全量构建和相关 CTest。
- 缺陷修复有复现测试；涉及句柄、并发、文件或网络生命周期时增加重复或压力验证。
- 源码、构建或补丁变更推送后手动触发相关 Linux/macOS CI，并查看最终结果。
- 有完整诊断基线和剩余诊断清单，不以无证据的“零警告”作为验收结论。

## 风险与回退

编码选项可能影响字符串解释，转换修复可能改变边界行为；逐类独立提交并验证，
出现回归时回退对应提交。第三方补丁须验证固定版本和重复应用规则。
