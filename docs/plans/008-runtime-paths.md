# 008：配置、日志与 PID 路径约定

## 状态

进行中。入口及根目录解析开始实施；配置加载、logger 和 Unix daemon 源码审计及旧入口路径
基准测试已建立。接口与实施进度见下文。本计划不依赖固定 Linux Runner 的性能基线，可独立推进。

## 背景

当前免安装发行包能够从任意工作目录启动，但启动器最终会切换到安装根目录，以保持 Skynet
现有相对模块路径可用。这解决了程序和模块定位，却没有给业务配置、日志和 daemon PID 文件
建立稳定的可写目录约定：相对路径仍可能落入发行目录，安装树也因而难以按只读方式部署。

配置、日志和 PID 的生命周期不同，不能简单放进同一个目录：

- 发行包内的示例配置是只读模板，不应在升级时承载业务修改；
- 业务配置由部署者管理，生命周期通常跨越一次程序升级；
- 日志是可轮转、可清理的运行数据；
- PID 是只在进程存活期间有效的短期状态，而且仅适用于 Unix daemon 模式。

## 目标

- 明确安装根目录、业务配置目录和运行状态目录的所有权及生命周期；
- 从任意工作目录启动时，同一配置始终解析到同一日志和 PID 位置；
- 支持将发行安装树设为只读，日志和 PID 不写入 `bin/`、`service/` 等程序目录；
- 保持 Windows、Linux 和 macOS 使用同一套配置表达方式，只在确有平台语义差异处区分；
- 为免安装开发、生产部署、容器和系统服务提供可预测的覆盖方式；
- 对目录不存在、不可写、PID 冲突和残留 PID 等错误给出明确诊断。

## 不在范围内

- 引入完整的配置中心、热更新系统或密钥管理系统；
- 规定业务配置文件的字段、拆分方式或发布流程；
- 实现日志轮转、采集、压缩和保留策略；
- 在 Windows 上用 PID 文件模拟 Unix daemon；
- 在本计划中实现 Windows Service、systemd 或 launchd 宿主；
- 自动迁移或覆盖用户已有的配置、日志和 PID 文件。

## 设计原则

### 目录职责

- **安装根目录**只存放程序、动态模块、Lua 库、随包服务、示例和许可证；正常运行不得要求其
  可写。
- **配置目录**由部署者持有。发行包只提供 `examples/` 模板，升级不得修改实际业务配置。
- **日志目录**只存放 logger 输出及其轮转产物，可以独立授权、挂载和清理。
- **运行目录**只存放进程存活期间的状态。首期只有 Unix daemon PID 文件，不承载持久业务数据。

推荐的逻辑布局如下；它表示职责而非强制系统绝对路径：

```text
安装根目录/                 只读
├─ bin/
├─ cservice/
├─ luaclib/
├─ lualib/
├─ service/
└─ examples/               配置模板

部署目录/                   可写或由部署系统管理
├─ config/                 实际业务配置
├─ log/                    持久运行日志
└─ run/                    临时 PID 等状态
```

### 路径解析

- 主配置文件继续由命令行显式指定，不依赖扫描当前目录或用户目录寻找配置；
- 程序和随包模块路径以安装根目录为基准，保持发行包可搬运；
- 日志和 PID 路径以明确的运行路径基准解析，不能因调用方当前工作目录不同而变化；
- 配置中的绝对路径继续有效，以便部署系统完全接管目录位置；
- 路径优先级必须只有一个权威顺序，并在诊断输出中显示最终解析结果；不叠加多个隐式搜索位置；
- 目录创建仅限已经明确选择的日志和运行目录，不递归猜测或创建配置目录。

### 平台边界

- Linux 和 macOS 前台运行不需要 PID 文件；仅配置 daemon 时使用 PID 路径；
- Windows 继续明确拒绝 `daemon` 配置，不创建无实际所有权保证的 PID 文件；
- 未来 Windows Service、systemd 和 launchd 集成由服务管理器跟踪进程，本计划不把 PID 文件设为
  跨平台公共契约；
- 容器默认前台运行并将日志写到标准输出；只有配置文件明确选择文件日志时才需要日志目录。

## 已确认的接口设计

采用显式启用的新目录模式，保留无选项入口的兼容行为。新入口为：

```sh
skyuv --runtime-paths [--install-root DIR] [--log-root DIR] [--run-root DIR] CONFIG
```

- 无 `--runtime-paths` 时保持现有启动、相对配置及日志/PID 基准；本阶段不自动迁移旧配置。
- 新模式先在调用方工作目录解析主配置为绝对路径。相对配置不存在时，才尝试安装根；
  随后定位安装根并切换工作目录，随包相对模块路径仍以安装根为基准。
- 配置根为最终主配置文件的父目录，不能被其他目录选项覆盖；`include` 继续相对包含它的
  配置文件解析，支持 Windows 驱动器绝对路径与两种分隔符。
- 安装根优先使用 `--install-root`，否则从可执行文件的 `bin/` 父目录定位；源码构建未使用
  发行布局时必须显式提供，不猜测源码树、用户目录或系统目录。
- 日志根和运行根的唯一顺序为：命令行 `--log-root` / `--run-root`，进程环境
  `SKYUV_LOG_ROOT` / `SKYUV_RUN_ROOT`，配置键 `skyuv_log_root` / `skyuv_run_root`，
  配置根下的 `log/` / `run/`。所有相对根目录值均以配置根为基准。
- `skyuv_install_root` 和 `skyuv_config_root` 为只读保留配置变量，在加载配置前以 Lua 值
  注入；目录参数不通过字符串拼接生成 Lua 源码。配置不得覆盖这两个变量。
- 解析后将四个最终根目录写入 Skynet 环境供服务查询。保持普通 Skynet `$NAME` 进程环境
  替换功能；不以修改全局进程环境的方式注入这些根目录。
- 默认 logger 的相对 `logger` 值以日志根为基准，绝对值保持原意，`nil` 继续标准输出；
  自定义 `logservice` 的启动参数不当成文件路径重写。
- Unix 相对 `daemon` 值以运行根为基准，绝对值保持原意。Windows 无论新旧模式均拒绝
  daemon，并且不为该配置创建运行目录或 PID 文件。
- 新模式只在相对文件 logger 或 Unix daemon 路径需要根目录时递归创建最终选定的日志/运行根；
  绝对文件路径不要求默认根目录存在或可写；
  不创建配置根、安装根，亦不自动创建 `logger` / `daemon` 文件名中额外的父目录。
  已有目录不更改权限，失败诊断包含最终路径；未启用的根目录不要求存在或可写。
- 启动前输出最终安装根、配置根及启用的日志/PID 路径，保留跨平台一致的诊断格式。

### Unix PID 生命周期

审计确认上游会先检查 PID，再 daemonize，最后加 `flock`，且正常退出直接 unlink；
锁文件 `FILE *` 没有明确生命周期，部分失败分支没有关闭已取得的描述符。此行为不足以直接
作为并发启动、残留和所有权的可靠保证。

实施时在 `src/platform/` 封装 Unix 特有锁与 daemon 原语，兼容入口共用修复后的所有权流程：
采用持久的 `<pidfile>.lock` 协调启动与退出，锁文件不删除以保持锁的 inode 稳定；
PID 文件也加锁，以兼容原版实例。两把锁持续持有到退出，失败路径释放文件和锁；
只删除本实例持有且路径仍指向原文件
的 PID 文件。活跃实例冲突必须明确失败，残留 PID 的判断结合锁与进程检查，不能仅凭文件存在。
macOS 保留上游不 fork 的兼容行为，Windows 保留明确拒绝。并发竞争、异常残留及退出删除
与下一次启动之间的竞争需有独立测试，不能仅用两个串行进程验证。

## 测试与验收

- 从两个不同工作目录使用同一配置启动，最终日志和 PID 路径完全一致；
- 安装树不可写时，前台标准输出模式和外置日志模式均能正常启动；
- 配置目录、日志目录、运行目录和安装目录分别包含空格时仍可运行；
- 文件日志可写入并通过 `skyuv.control.reopen_log()` 重开；
- 日志目录不可用时启动失败且诊断包含最终路径，不留下半初始化 logger；
- Linux/macOS daemon 能发现 PID 冲突并在正常退出后清理 PID 文件；
- Windows 配置 daemon 时继续快速失败，不创建 PID 文件；
- 安装、解压和现有三平台运行时测试保持通过。

## 风险与回退

- 上游配置环境替换可能发生在安装根定位之前：先保持现有启动行为，通过启动器传入已解析值；
- 改变相对路径基准可能破坏既有配置：保留显式绝对路径，并为旧行为提供有期限的兼容入口；
- 自动创建目录可能掩盖拼写错误或越权：只创建最终选定的可写目录，失败立即报告；
- PID 文件存在不等于进程存活：实现前必须复核上游的锁定、残留检测和删除语义，不只测试文件存在；
- 若统一目录变量需要修改第三方代码，优先在 skyuv 启动适配层完成；无法适配时维护独立补丁。
