# 006：性能和稳定性

## 状态

进行中。

## 背景与目标

阶段 4 完成后，便携 Skynet 已在 Windows、Linux 和 macOS 通过主要功能与生命周期测试。
本阶段不再扩大公开能力，而是验证 libuv 网络层在高并发、资源积压和长时间运行下的正确性，
并测量其相对 Linux 原版 Skynet 的性能影响。

目标：

- 建立可重复的 Actor、TCP 和 UDP 基准入口；
- 覆盖大量连接、多 worker 发送、背压、ID 复用和带未完成请求退出；
- 使用 Sanitizer 和资源计数发现竞态、越界、泄漏及悬空回调；
- 在同一 Linux 环境对照原版 epoll 与 skyuv/libuv 的吞吐、延迟、CPU 和内存；
- 以结构化结果保存环境、参数和统计量，为后续优化提供证据。

## 不在范围内

- 为追求基准分数改变 Skynet 的 Actor、消息调度或公开 Lua API；
- 在建立可重复基线前承诺固定性能比例；
- 用共享 GitHub Actions Runner 的波动数据阻止合并；
- 互联网广域网、跨机集群或特定云厂商性能调优；
- TLS、Windows Service、安装包和正式发布流程；
- 没有测量依据的直接写、批处理、自旋锁或分配器替换。

## 已确认决策

### 正确性与性能分离

- 压力测试以断言、退出状态和资源归零为准，可以进入三平台 CTest；
- 性能基准只采集数据，不在共享 Runner 上使用绝对耗时或吞吐作为硬门槛；
- Linux 原版和 skyuv 必须在同一台机器、同一轮次、相同编译模式和负载参数下运行；
- 基准默认使用 Release，调试构建和 Sanitizer 只用于正确性诊断；
- 原版与 skyuv 使用相同分配器策略进行主对照，分配器差异另列为独立维度。

### 测量与统计

- 每个场景包含预热，随后至少运行 5 轮；保存每轮原始结果；
- 吞吐报告中位数，延迟报告 p50、p95、p99 和最大值，不只报告平均值；
- CPU 记录用户态、内核态和总 CPU 时间；内存记录峰值常驻集；
- 结果包含提交、编译器、构建类型、分配器、操作系统、CPU、内存、libuv/Skynet 版本和参数；
- 基准输出稳定 JSON，面向人的 Markdown 报告由结果生成，不维护两套手写数据。

### 平台分工

- Linux 是原版 epoll 与 skyuv/libuv 性能对照的权威平台；
- Windows 和 macOS 运行功能等价的稳定性压力，证明生命周期和平台适配正确；
- GitHub Actions 运行缩短版压力与 Sanitizer；长时 soak 和正式性能采样手动触发；
- 基准进程固定本机回环，避免外部网络噪声；需要跨机数据时另立计划。

## 场景与指标

### Actor 与调度

- 单 Actor ping-pong：消息吞吐与往返延迟；
- 多生产者向单消费者发送：吞吐、公平性和队列积压；
- 多 Actor 环形传递：调度吞吐、CPU 和尾延迟；
- 定时器集中触发：到期偏差、处理吞吐和退出完整性。

### TCP 与 UDP

- TCP 长连接 echo：不同消息尺寸、并发连接数和 worker 数下的吞吐与延迟；
- TCP 短连接：持续 connect/accept/close，验证端口、ID 和 handle 回收；
- 多 worker 并发 send：检查每生产者顺序、完整性和命令队列竞争；
- 慢接收端：制造写队列积压，验证 warning、背压、关闭和峰值内存；
- 写中 close/exit：保留未完成 connect/read/write 并重复退出；
- UDP request/reply：不同数据报尺寸下的包速率、丢包和来源地址处理。

### 生命周期与资源

- socket ID 快速复用并注入迟到回调，检查 generation 隔离；
- 节点、runtime、cluster 和 harbor 重复启动停止；
- 运行前后比较线程数、打开句柄/文件描述符和分配计数；
- 短压力默认按秒或次数终止，长时 soak 默认 1 小时并允许显式配置；
- 所有失败输出随机种子、参数和最后状态，使问题可以复现。

## 影响范围

- `benchmarks/`：新增独立基准夹具、负载驱动和结果 schema，不与功能测试混放；
- `tests/`：新增可在合理时间内完成的确定性压力与资源归零测试；
- `CMakeLists.txt`、`CMakePresets.json`：注册基准目标及 ASan/UBSan 配置；
- `.github/workflows/`：增加缩短版 Sanitizer 验证和手动长时运行入口；
- `docs/records/`：保存基准环境、原始结果索引、统计摘要和接受差异；
- socket runtime、平台层和 Skynet 适配层仅在数据证明瓶颈后进行聚焦修改。

## 实施顺序

1. 定义统一基准参数、JSON schema、环境元数据和退出码；
2. 建立不依赖 Skynet 上层的 socket runtime 压力测试，覆盖 ID、命令队列和关闭竞态；
3. 建立 Actor、TCP echo、短连接、慢接收端和 UDP 基准夹具；
4. 让同一客户端驱动原版 Skynet 与 skyuv，避免客户端实现成为对照变量；
5. 增加 Linux ASan/UBSan 配置和 CI，保留现有 TSan；
6. 将缩短版稳定性测试接入 Windows、Linux 和 macOS CTest；
7. 增加手动长时 soak 工作流，上传日志和结构化结果；
8. 在固定 Linux 环境采集首轮原版/skyuv 基线并记录噪声范围；
9. 根据基线识别热点，只对有证据的瓶颈实施独立优化；
10. 优化前后使用同一参数复测，记录收益、代价和未改善场景；
11. 确定后续性能回归阈值并完成阶段验收。

每项优化必须与基准设施分开提交。修改源码、测试、构建或工作流后，推送并手动运行相关
Linux/macOS CI；Windows 使用本机 MSVC 完整验证。

## 实施进度

- 步骤 1 已完成：统一 duration、warmup、iterations、seed、实现、构建、分配器和输出参数；
  定义退出码、环境元数据、版本化 JSON schema、原子结果写入及跨平台协议自测。
- 步骤 2 已完成首批确定性 runtime 压力：使用测试专用小槽位表验证真实 ID 回绕与旧代际隔离，
  并覆盖多线程同时关闭只产生一次事件、退出后并发发送拒绝和自有缓冲区释放计数归零。
- 步骤 3 已开始：完成首个 TCP 长连接 echo 夹具；同一客户端可驱动 skyuv 与原版 Skynet，
  支持预热、多轮、可配置消息尺寸、逐次内容校验、吞吐和延迟分位数结构化输出。
- TCP 短连接夹具已完成：每次操作独立执行 connect、单次 echo 和 close，复用相同服务端与
  结果协议，用于测量连接建立、接受、关闭和 socket ID 回收的综合成本。
- 慢接收端与背压夹具已完成：服务端持续写入并记录 Skynet 写队列 warning，客户端通过暂停、
  小块读取和读取间隔制造积压，保存每轮接收字节数与吞吐；正式运行需同时保留服务端日志。
- UDP request/reply 夹具已完成：同一客户端逐包校验响应来源与内容，记录发送、接收、超时丢包、
  包速率和成功响应延迟分位数；首期固定一个在途请求以建立稳定基础数据。
- Actor 单路 ping-pong 夹具已完成：两个独立 Lua 服务通过同步 call/return 往返，使用纳秒级
  `skynet.hpc()` 记录吞吐与延迟；同一 Python 启动器可运行 skyuv 和原版 Skynet。
- Actor 多生产者夹具已完成：默认 4 个生产者并发向单消费者异步发送，通过同源 barrier 保证
  消费完成，校验消息计数并记录总吞吐、生产者最小/最大消息数及公平性比例。
- Actor 环形传递夹具已完成：默认 8 个 Actor 顺序转发单个令牌，以 hop 统计调度吞吐，并以
  完整环路记录 p50、p95、p99 和最大延迟，Actor 数量可配置。
- 定时器集中触发夹具已完成：每轮为可配置数量的定时器设置同一截止时间，验证回调完整性，
  并记录计划截止时间到实际执行时刻的 p50、p95、p99 和最大偏差。
- 写入期间退出夹具已完成：客户端停止读取，服务端排队约 32 MiB 写入后接收外部停止信号，
  验证 Windows Console Break 与 Unix SIGTERM 均能回收未完成请求并正常退出。
- 步骤 4 已开始：Actor ping-pong 已提供配对对照编排器，同一进程以相同参数依次驱动 skyuv
  与原版 Skynet，分别保存原始 JSON，并生成记录公共参数和结果路径的配对清单。
- TCP 长连接 echo 已接入配对编排：同一客户端以相同消息尺寸和测量参数依次驱动两个服务端，
  保存各自原始结果、服务端日志以及公共参数清单，Linux CI 负责验证原版对照可运行。
- TCP 短连接已复用同一配对编排：每次操作执行 connect、echo、close，双方共享服务端生命周期、
  消息尺寸和测量参数，并各自保存原始结果与服务端日志。
- 慢接收端与背压已接入配对编排：客户端以相同暂停、读取间隔和读取块尺寸驱动双方服务端，
  除保存接收吞吐外，还要求双方日志均出现写队列 warning 标记。

## 测试与验收

正确性门槛：

- 三平台缩短版压力测试全部通过，无崩溃、挂起、数据损坏或资源持续增长；
- ASan/UBSan 不报告越界、释放后使用、双重释放或未定义行为；
- TSan 不报告项目自有代码中的已知数据竞争；
- 高并发关闭和退出后，socket 槽位、未完成请求和自有缓冲区计数归零；
- 原版与 skyuv 接收相同参数并产生语义等价的响应和计数。

性能门槛分两步确定：

1. 首轮基线至少在两个独立时段采集，先量化同机噪声，不据单次结果设阈值；
2. 基线稳定后，在本计划完成记录中写明每个核心场景允许的回归范围，才启用自动比较。

阶段完成还必须满足：

- 基准命令、环境和结果可由他人复现；
- 至少完成 Actor、TCP 长连接、TCP 短连接、背压和 UDP 五类原版对照；
- Windows、Linux 和 macOS 均完成长时稳定性运行，时长与负载被记录；
- 发现的性能差异有测量解释或明确接受，不以隐藏场景或降低负载规避；
- 第三方工作树干净，严格警告保持开启。

## 风险与回退

- 共享主机调度和频率变化会污染结果：性能结论只采用固定环境多轮对照；
- 客户端可能先成为瓶颈：记录客户端 CPU，并支持多进程或预生成负载；
- Sanitizer 会改变时序：其结果只用于正确性，不与 Release 性能数据混合；
- 长时测试失败成本高：所有场景先提供分钟级复现模式，再扩大时长；
- 优化可能改变事件语义或所有权：先运行阶段 0 至阶段 4 回归，失败即回退该优化；
- 如果基准噪声大于预期差异，先改善测量方法，不对实现作无依据调整。

## 未决问题

以下参数由首轮基线确定，不阻塞基准设施实施：

- 固定性能主机的 CPU、频率策略和可用核心；
- 各消息尺寸、连接数、worker 数和正式 soak 时长；
- 主对照使用 jemalloc 还是系统分配器，以及分配器专项矩阵；
- 基线稳定后的吞吐、尾延迟、CPU 和内存回归阈值；
- 是否需要在阶段 6 引入专用自托管 Runner 保存长期趋势。
