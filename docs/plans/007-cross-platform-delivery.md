# 007：跨平台交付

## 状态

草案。阶段 5 的三平台长时稳定性已完成，权威性能基线仍等待固定 Linux Runner；本计划可先完成
安装与打包审计，但正式发布验收依赖阶段 5 收口。

## 背景与目标

skyuv 已能在 Windows、Linux 和 macOS 构建、启动并通过功能与长时稳定性验证。当前运行依赖
构建目录布局，仓库尚无 CMake `install()` 或 CPack 规则，不能把构建目录直接视为可发布产品。

本阶段目标：

- 定义三平台一致、可搬运的安装目录；
- 通过 CMake 安装主程序、C 服务、Lua C 模块、Lua 库、示例配置和必要许可证；
- 生成 Windows ZIP、Linux tar.gz 和 macOS tar.gz；
- 验证产物解压后不依赖源码树或构建树即可启动最小节点；
- 建立版本、校验和、发布说明和 GitHub Release 工作流；
- 记录不可等价的平台能力和迁移方式。

## 不在范围内

- 在没有权威基线时进行网络性能优化；
- 提供 ABI 稳定承诺或兼容任意第三方二进制 Lua 模块；
- Windows MSI、macOS PKG/DMG、代码签名、公证和自动更新；
- Windows Service 宿主和 Unix 系统服务单元；
- 打包数据库、TLS 证书或业务服务配置；
- 将编译器运行库许可之外的系统组件复制进产物。

## 已确认决策

### 交付形式

- 首个交付版本使用免安装压缩包，不引入平台原生安装器；
- CMake `install()` 是唯一的产物装配入口，CPack 只封装安装树；
- 三个平台采用相同逻辑目录，平台扩展名由 CMake 自然决定；
- Release 产物不得包含测试程序、构建缓存、对象文件或本机绝对路径；
- Debug 符号和崩溃诊断产物若需要发布，应作为独立 artifact。

### 运行时布局

目标安装树：

```text
skyuv/
├─ bin/                 # skyuv_skynet_portable 与平台运行库
├─ cservice/            # Skynet C 服务动态库
├─ luaclib/             # Lua C 模块，保留模块子目录
├─ lualib/              # Skynet 与 skyuv Lua 库
├─ service/             # 可随发行版使用的 Lua 服务
├─ examples/            # 最小启动与网络示例配置
├─ include/skyuv/       # 需要公开的 skyuv C 接口
└─ licenses/            # skyuv 与随包第三方许可证
```

- 默认配置使用相对安装根目录的搜索路径；
- Windows DLL 与主程序放置规则以无需修改系统 `PATH` 即可启动为准；
- 不安装内部测试头文件和 Skynet 未承诺稳定的私有头文件；
- 第三方源码不随二进制包分发，但必须包含相应许可证文本和版本清单。

### 发布与验证

- 版本以根 CMake `project(... VERSION ...)` 为唯一来源；
- 发布工作流只允许手动触发或由明确版本标签触发；
- 每个平台上传压缩包及 SHA-256 校验和；
- 发布前在干净临时目录解压并运行启动、TCP echo 和正常退出测试；
- GitHub Hosted 负责可搬运性验证，固定 Linux 性能机不承担发布构建。

## 当前审计

- 根项目版本为 `0.1.0`；
- 已定义 `Runtime` 组件的首批 CMake `install()` 规则，覆盖主程序、4 个 C 服务和 7 个
  Lua C 模块；
- 尚未接入 CPack；
- 当前示例配置主要引用源码树或构建树路径；
- 最小启动闭包和支持的运行时闭包已经完成审计，详见
  [`../records/delivery-runtime-closure-audit.md`](../records/delivery-runtime-closure-audit.md)；
- 首版确定只交付运行时组件，公共头文件等待 ABI 评审后再作为开发组件加入；
- 动态模块已能在三平台构建，但尚未验证安装树中的相对搜索路径；
- 发行构建推荐三平台统一静态链接 libuv，最终决定以安装后动态依赖检查为准；
- CI 已覆盖三平台构建和运行，可复用为安装后冒烟测试基础。

## 实施顺序

1. 已完成：枚举最小运行闭包，区分必须安装、开发可选和不得发布的文件；
2. 已完成：定义安装目录变量和 `Runtime` 组件，接入主程序、C 服务及 Lua C 模块；
3. 安装 Lua 库、服务、示例配置、公共头文件和许可证；
4. 生成只使用安装树相对路径的发行配置；
5. 增加“安装到临时前缀后启动”的三平台测试；
6. 接入 CPack ZIP/TGZ 生成器并验证压缩包内容清单；
7. 在干净目录解压，运行最小节点、TCP echo 和正常退出测试；
8. 增加版本一致性、SHA-256 和第三方许可证完整性检查；
9. 建立手动 Release 工作流，上传三平台产物与校验和；
10. 编写安装、启动、迁移和平台限制指南；
11. 完成阶段 5 后执行候选版本全量验收并收口本阶段。

## 测试与验收

- `cmake --install` 在三平台成功，且安装前缀可由调用者指定；
- 安装树不包含源码树、构建树或用户目录绝对路径；
- 压缩包解压到含空格的路径后仍可启动；
- 最小节点、Lua 模块加载、TCP echo 和正常退出均从安装树通过；
- Windows、Linux、macOS 产物都包含版本清单、许可证和 SHA-256；
- 严格警告、现有三平台 CI 和稳定性测试保持通过；
- 发布文档只描述已经随产物验证的能力和明确限制。

## 风险与回退

- Lua 搜索路径可能泄漏构建目录：安装后测试必须在源码树之外运行；
- 多配置生成器的配置子目录可能进入产物：安装规则必须使用目标表达式而非硬编码路径；
- Windows DLL 搜索规则与 Unix 不同：首版优先使用主程序邻接布局并做干净环境测试；
- 第三方许可证遗漏会阻止发布：许可证清单作为硬性校验，不以人工记忆维护；
- 平台压缩格式差异会增加脚本分支：首版只使用 CPack 已支持的 ZIP/TGZ；
- 若安装边界发现内部 ABI 暴露过多，先缩小开发组件，不扩大稳定性承诺。

## 未决问题

- Windows 是否需要随包携带特定 MSVC 运行库，或只声明系统前置条件；
- 是否为 Lua 服务提供可写的独立配置/日志目录约定；
- 版本标签采用 `v0.1.0` 还是不带前缀的 `0.1.0`；
- 阶段 5 权威基线完成前，是否只生成候选 artifact 而不创建正式 Release。
